# 项目决策

## 2026-10-15：个人构建更新提示方案

- **状态：已采纳；代码端已实施，服务器传输待确认。**
- **背景：** 用户在 Chrome/Edge 以“加载已解压扩展”方式使用改版；`package.json` 的 `2.8.8` 来自原项目。希望 GitHub 推送后自动构建，将来传送到自有服务器，并在管理页和弹窗显示新构建下载入口。
- **决定：** 使用独立的个人构建号，随扩展包保存；服务器发布静态 `latest.json`。只有远端构建号更大才提示。推送代码但未递增构建号时仍允许上传，不显示更新提示。保留现有浏览器更新事件的“立即升级”按钮。
- **理由：** 自有服务器只需托管静态文件；用户可独立于原项目版本控制提示时机；符合已解压扩展的手动更新流程。
- **影响：** 管理页与弹窗需要共享检查逻辑；CI 需要生成包和版本元数据。服务器地址、目录、传输协议尚未提供，实际传输配置待确认。GitHub Release API 方案增加对 GitHub 发布流程和 API 的依赖，未采用。
- **实施边界：** `master` 推送后先由 GitHub Actions 保存 ZIP 与 `latest.json` 工件。仓库变量 `NICETAB_UPDATE_MANIFEST_URL` 在编译时注入扩展；变量缺失则跳过检查。未来上传服务器时必须先传 ZIP，最后更新清单。当前在用户选择下直接于 `master` 检出目录实施，没有创建 worktree。
